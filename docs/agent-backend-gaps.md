# Agent backend gaps

Account-level GitHub setup is authoritative for onboarding and future repository selection. Every direct or invite signup installs the GitHub App before plan completion; an account may hold multiple personal or organization installations, with no GitHub OAuth/user token stored. New session creation resolves the browser's opaque installation association against the signed-in user, verifies the chosen repository's default branch and head before writing, reserves session/repository/candidate state together, and provisions the candidate before opening the normal lobby. A post-reservation remote failure remains visible and retryable; exact branch/SHA reconciliation never forces or deletes a mismatched ref. Removing an account association affects future choices only, while signed GitHub uninstall/suspension events revoke matching account associations and live session repository state.

The current backend persists collaboration state, repository/candidate state, preflight history, agent runs, generated-agent lifecycle, integrated-run rollback groups/audit, conflict-resolution audit, and final review/merge audit state. Candidate name and description default from the session title/objective, remain durable, produce a safely slugged server-owned ref, and title/describe the draft pull request. An owner can start or cancel an agent against the exact candidate SHA. Passing writable runs with file changes are bundle-validated, published independently, and integrated serially into the active candidate. Successful no-change tasks retain their output and complete without publication. Review has Files and Prompts modes backed by candidate-wide contribution reads: changed files identify the human engineer(s), software agent, and originating prompt group, while prompt detail shows the exact historical run diff. Before final merge, the session owner, the run's agent owner, or the engineer who authored every prompt in one integrated group may remove that group. The owner may also atomically remove all solely-authored groups for one engineer or every active group produced by one software agent; mixed-author engineer groups are explicit exclusions. The exact candidate SHA and target set are previewed and revalidated, targets revert newest-first into one deterministic inverse commit, and a separate trusted publisher performs the expected-SHA push. Original prompts, runs, branches, and rollback attempts remain durable, with completed groups under Review History. The first integration creates one draft pull request; later runs update that same candidate/PR. A real GitHub integration `409` creates one durable conflict case. By default, a specialized resolver inherits the source agent/provider/model and agent-owner credential policy, reconstructs a genuine three-way merge from the source archive, retained verified bundle, and latest candidate, then uses the existing publication pipeline. The resolver must stop for mutually exclusive authored outcomes and may request one to three answers in Review; only the session owner or a current original prompt author may submit them. Two automatic attempts are allowed after each human response; the owner controls automation and manual retry. GitHub remains authoritative for PR head/base, files, checks, readiness, mergeability, protection enforcement, squash merge confirmation, and branch heads used for safe cleanup.

Review app preview is implemented but unavailable while `REPOSITORY_PREVIEW_ENABLED=false`, which remains the setting in both production and development. D1 owns one generation-protected 60-minute lease per session and a three-preview environment cap; `RepositoryPreviewWorkflow` provisions the exact synchronized candidate and keeps an older ready generation available while its replacement provisions or fails. Successful integration and rollback request an automatic rebuild. Terminal session, candidate, and repository transitions revoke the lease. Durable cleanup intents let the 10-minute cron retry failed Sandbox destruction.

Preview scope is deliberately narrow: one JavaScript application at the repository root, exactly one npm, pnpm, Yarn, or Bun lockfile, and a nonempty `dev` or `start` script, preferring `dev`. Dependency lifecycle scripts are suppressed. Install and runtime use the credential-free execution namespace: install may CONNECT only to `registry.npmjs.org:443`, and runtime has no outbound network. A root setup shell raises private loopback, then setpriv drops all capabilities before the candidate. One detected HTTP listener is relayed through a locked Unix socket to a trusted outer TCP port.

The Claude-provider milestone (per-user encrypted credentials, the Claude runner, provider selection, session-scoped imported skills, and owner-configured remote MCP servers) is implemented behind `CLAUDE_RUN_ENABLED=true`; Kimi and Gemini are similarly implemented behind their provider flags. Sandbox image `v12` uses a credential-free namespace containing the whole provider, native file tools, post-agent Git, and preview install/runtime. An outside broker holds scoped gateway/MCP authority; trusted publication remains in a separate Sandbox. Exact-image tests cover file/process/network boundaries, broker transport, cancellation, and CLI startup (see `docs/josh-beta-runtime-isolation.md`). Production's global `AGENT_RUN_ENABLED` gate is enabled for admitted beta testers after that image deployed successfully. OpenAI, Claude, Kimi, and Gemini are available; GLM, Qwen, and DeepSeek remain disabled until their independent live-key acceptance passes. Every model gateway re-reads D1 and permits upstream model traffic only while the run is exactly `running`; `cancel_requested` retains bounded shutdown activity/context access but loses model-spending authority immediately. Grok (xAI) remains deliberately excluded. Still deferred: `stdio` MCP transports for user-configured servers, the Codex and Gemini serializers for user-configured MCP servers, skills for non-Claude-runner providers, claude.ai skill sync, and token/cost metering (runners capture `usage` into result.json; `parseCodexResult` discards it).

The following capabilities require a separate trusted agent-runtime and repository integration and are intentionally not simulated:

- Agent-authored chat messages. (Provider and model selection are implemented: the dialog offers every provider whose rollout flag is on and every model in that provider's closed `PROVIDER_MODELS` allowlist. User-managed provider credentials are implemented — per-user encrypted keys in `user_provider_credentials`, resolved per run exclusively from the agent owner's personal API key. See AGENTS.md's 2026-08-21 and 2026-08-24 decision-log entries.)
- Deployment and generic support for merge queues or non-squash merge methods.
- Generic artifact download UI beyond the per-run raw-log expander.
- Agent ownership transfer and automatic queue consumption/retry. Explicit completion, soft removal, and user-triggered retry are implemented. New persistent agents are self-owned; task edits remain collaborative, while model/billing edits and Resume require the recorded agent owner. Any member may Pause/Stop, owner-only bulk pause/stop remains, and bulk resume affects only caller-owned agents. Migration `0042` pauses legacy creator/owner mismatches until recorded-owner consent. Provider stays uneditable by design — delete and recreate. Per-agent reasoning effort (`output_config.effort`) stays deferred: the runners do not thread a second axis today. Generated workers remain system-metadata-owned, non-editable, and non-deletable; Concierge activation/retirement and concurrent allocation remain exclusively router-controlled.

Repository connection, active candidate/PR identity, bounded latest-preflight data, conflict cases/questions, auto-dispatch/provision/provider settings, active agents, and the latest 20 caller-visible run summaries are included in `FloorSnapshot`; full logs and bundles remain excluded. Queue items carry a separate caller-specific rollback descriptor so older integrated prompts remain actionable beyond that run-summary bound. Candidate-wide Review contribution summaries/details are fetched through paginated member-authorized routes (25 by default, 100 maximum), not packed into `FloorSnapshot`. Deprovisioned generated agents are hidden from active targeting and context, while historical queue/run attribution remains visible. Run branches, publication/integration SHAs, conflict attempts, and independent attribution stay visible. Resolved source conflicts no longer remain as active Review warnings.

`FloorSnapshot.preview` is nullable and omitted from presentation while the rollout gate is off. When enabled, it reports provisioning, ready, failed, or derived expired state, exact target and visible candidate SHAs, runtime detection, failure text, URL, and lease timestamps. Stopped preview is represented as `null`.

## Live run activity streaming

Runs stream a bounded activity feed while Codex executes. The in-sandbox runner (`scripts/codex-runner.mjs`) normalizes Codex thread events (reasoning, commands, file edits, agent messages, MCP tool calls, errors) and POSTs batches to `POST /runtime/run/events`, authenticated by a run-scoped gateway token with the `events` operation and gated on run status `running`/`cancel_requested`. Events persist in `agent_run_events` with runner sequences starting at 1,000,000; coarse workflow-stage events keep the per-run `MAX+1` scheme, so the merged timeline stays chronological under `ORDER BY sequence`. Accepted events broadcast to session members as a `run.activity` presence event without bumping `floor_revision`; members catch up or paint initial state via `GET /api/sessions/:id/runs/:runId/events?after=<sequence>`. Bounds: detail ≤ 2,000 chars, ≤ 50 events and 256 KB per POST, ≤ 2,000 runner events per run with a `truncated` sentinel; telemetry failures never fail the run.

## Session context and the live re-read tool

Every dispatched agent's prompt is a unified session brief (`db/session-context.ts` + `lib/session-context.ts`): its own request, every other agent and human on the floor, already-integrated work, other runs in flight with their live file edits, the rest of the queue, blocked/failed runs, and recent public team chat — bounded to 24,000 characters, direct messages structurally excluded (the D1 read never takes a `userId`). The exact rendered prompt is persisted as an `agent_run_artifacts` row of kind `prompt` and retained for internal audit; normal agent cards and run history do not expose the session brief. A long run can re-read current floor state through a read-only `openfloor_session_context` MCP tool exposed by the Sandbox (`scripts/openfloor-mcp.mjs`), backed by `GET /runtime/run/context` (a `"context"`-operation gateway token, 60-minute TTL). Pooled run sandboxes are keyed by `RUN_SANDBOX_IMAGE_VERSION` so a stale pooled container can never be claimed by a live run after a `Dockerfile.sandbox` change — bump that constant whenever the image's contents change.

## Thread resume and PR feedback nudges

A retry or re-run of a queue item (or a nudge naming its `source_run_id`) resumes the earlier attempt's provider thread when `lib/run-resume.ts` finds an eligible run with a persisted `session_store` artifact (Codex, Claude, and Qwen Code runners — `resumableProvider`); Gemini runs always start fresh. Failing checks, unresolved review threads, and changes-requested reviews on the candidate PR become router-originated queue items through `lib/candidate-feedback.ts` after the matching webhook. Deliberately not built: a delta brief on resume (the full brief plus a preamble is sent), CI log tails in nudges (needs an Actions:read App permission), and a periodic PR-fact reconciler between webhooks.

## Credential kinds — deliberately deferred pieces

Per-user credentials are keyed `(user_id, provider, kind)` with kinds `api_key` and `oauth` (pasted Claude setup token / Kimi Code plan key / ChatGPT auth bundle), and each agent's `credential_kind` names which one its runs bill. Kimi Code plan support (2026-08-26 decision-log entry) shipped on the vendor's documented surface without a purchased-plan spike — the plan waitlist blocked a scratch account — so its connect-time probe stays absent (`validated_at = null`) and production members' plan runs are the acceptance. Alibaba's Coding Plan (`sk-sp-…` keys on a separate `coding-intl` base, the natural `oauth` kind for `qwen`) is deliberately not offered until Spike Q2 completes a real run on a plan key — see the 2026-08-28 Qwen decision-log entry. Anthropic setup tokens validate on connect and use their native upstream auth. The openai gateway sends only the ChatGPT bundle's access token plus an injected account id upstream — never the stored bundle or refresh token — and refreshes under a strictly increasing conditional D1 version. Only the outside broker receives the short-lived gateway token; the provider and every tool receive local URLs and placeholders within the execution namespace. Global agent execution is available only to admitted product users and still obeys provider, membership, ownership, quota, cancellation, and repository gates. Deliberately not built: a connect-time probe for a ChatGPT bundle; allowlisting `GET /v1/models` on the openai gateway; more than one row per user+provider+kind; automatic payer failover; live model-list fetching or plan-entitlement modeling; and another member's credential status/quota display.

## Qwen (Alibaba Cloud) and DeepSeek — built keyless, gated until the live-key spikes pass

Both providers ride one Qwen Code runner (`scripts/qwen-runner.mjs`) and the OpenAI-chat-compat gateway, fully wired and worker-tested behind `QWEN_RUN_ENABLED`/`DEEPSEEK_RUN_ENABLED` (false). Spike Q1 (the CLI against a stub, srt posture, resume, settings precedence) passed keyless; what remains needs a scratch key per vendor — Spike Q2 (DashScope `GET /models` ids, SSE/usage framing, tool calling, one real run) and Spike D1 (the same against `api.deepseek.com`, choosing the default model from behavior). `PROVIDER_MODELS` and `MODEL_PRICING` carry doc-banked ids/prices flagged for that re-verification. Not built: session skills and user-configured MCP servers for the Qwen runner (Claude-runner features), a periodic vendor model-list fetch (`PROVIDER_MODELS` stays a constant on purpose), and the Coding Plan `oauth` kind above.

## Grok (xAI) — excluded three times, on every known route

The Anthropic-compat route died on xAI rejecting system-role messages (2026-08-24 decision log); the Responses route died the same day on xAI rejecting the `"content": null` Codex 0.148.0 writes on replayed reasoning input items (400 "Could not decode the compaction blob" on every thread's second request — Spike B). The 2026-08-26 re-spike (ENG-118) closed the rest: both failures reproduce byte-identically today; the chat wire is gone from the Codex binary itself (`@openai/codex-sdk@0.149.1`, the latest, vendors `` `wire_api = "chat"` is no longer supported. ``); reasoning effort `none` is vendor-rejected (`This model does not support 'reasoning_effort' value 'none'.` for grok-4.5 and grok-4.6); and the SuperGrok/X Premium subscription credential (Grok Build's `~/.grok/auth.json` OAuth bundle) is short-lived + refresh-based, so it fails the paste-a-credential requirements. All blockers are upstream (xAI tolerance or a Codex serialization change); gateway body rewriting stays rejected. `parseCredentialProvider("grok")` stays pinned null. Reopen conditions are enumerated in the 2026-08-26 decision-log entry.

## Deployment order

1. Run `npm audit --omit=dev` and `npm test`.
2. Apply D1 migrations with `npx wrangler d1 migrations apply DB --remote`.
3. Build with `npm run build`.
4. Verify the production artifact with `npm run verify:deploy-artifact`.
5. Deploy with `npx wrangler deploy --config dist/server/wrangler.json`.
6. Smoke-test the owner/member flow from `docs/github-production.md` against only the disposable acceptance repository, including two consecutive integrations into one draft PR, automatic multi-file conflict resolution, a resolver question answered by an original author or owner, unrelated-member waiting UI, owner-only manual resolution with automation off, ready-for-review, protected squash merge, exact-SHA cleanup, a fresh candidate cycle, reload recovery, cancellation, and a failing retryable run.

Known follow-up: Phase 5 discard is still reported by the production UI as unsuccessful in the acceptance repository after the authentication correction. Keep its expected-SHA safety checks intact and diagnose it in the separately requested ticket; it is not part of Phase 6 acceptance.

## Personal billing and Review history

Generated workers and Concierge are owned by the prompt author and use that person's account default API provider. Personal membership automation preferences and the owner's session gates both apply. Missing keys hold only affected work. Persistent agents are private by default; explicit owner sharing permits teammates to spend the owner's key. Subscription connections and platform-funded execution are unavailable; existing encrypted subscription records and spend history are retained.

Review retains its command bar and three panes without a candidate. Member-authorized prompt history includes retained dismissed and legacy merged prompts across candidate cycles, with paginated exact run-attempt diffs. Prompt merging remains unavailable through both UI and API.
