# Agent backend gaps

Account-level GitHub setup is authoritative for onboarding and future repository selection. Every direct or invite signup installs the GitHub App before plan completion; an account may hold multiple personal or organization installations, with no GitHub OAuth/user token stored. New session creation resolves the browser's opaque installation association against the signed-in user, verifies the chosen repository's default branch and head before writing, reserves session/repository/candidate state together, and provisions the candidate before opening the normal lobby. A post-reservation remote failure remains visible and retryable; exact branch/SHA reconciliation never forces or deletes a mismatched ref. Removing an account association affects future choices only, while signed GitHub uninstall/suspension events revoke matching account associations and live session repository state.

The current backend persists collaboration state, repository/candidate state, preflight history, agent runs, generated-agent lifecycle, integrated-run rollback groups/audit, conflict-resolution audit, and final review/merge audit state. Candidate name and description default from the session title/objective, remain durable, produce a safely slugged server-owned ref, and title/describe the draft pull request. An owner can start or cancel an agent against the exact candidate SHA. Every passing run is bundle-validated, published independently, and then integrated serially into the active candidate. Review has Files and Prompts modes backed by candidate-wide contribution reads: changed files identify the human engineer(s), software agent, and originating prompt group, while prompt detail shows the exact historical run diff. Before final merge, the session owner, the run's agent owner, or the engineer who authored every prompt in one integrated group may remove that group. The owner may also atomically remove all solely-authored groups for one engineer or every active group produced by one software agent; mixed-author engineer groups are explicit exclusions. The exact candidate SHA and target set are previewed and revalidated, targets revert newest-first into one deterministic inverse commit, required checks run, and a separate trusted publisher performs the expected-SHA push. Original prompts, runs, branches, and rollback attempts remain durable, with completed groups under Review History. The first integration creates one draft pull request; later runs update that same candidate/PR. A real GitHub integration `409` creates one durable conflict case. By default, a specialized resolver inherits the source agent/provider/model and agent-owner credential policy, reconstructs a genuine three-way merge from the source archive, retained verified bundle, and latest candidate, then uses the existing checks and verified publication pipeline. The resolver must stop for mutually exclusive authored outcomes and may request one to three answers in Review; only the session owner or a current original prompt author may submit them. Two automatic attempts are allowed after each human response; the owner controls automation and manual retry. GitHub remains authoritative for PR head/base, files, checks, readiness, mergeability, protection enforcement, squash merge confirmation, and branch heads used for safe cleanup.

The Claude-provider milestone (per-user encrypted credentials, the Claude runner with its verified sandbox posture, provider selection, session-scoped imported skills, and owner-configured remote MCP servers) is live behind `CLAUDE_RUN_ENABLED=true`; see AGENTS.md's 2026-08-21 decision-log entries. Kimi (Moonshot, same runner via `/runtime/kimi`) and Gemini (own CLI runner) are live behind `KIMI_RUN_ENABLED=true`/`GEMINI_RUN_ENABLED=true`; Grok (xAI) is deliberately excluded — its Anthropic compat rejects the CLI's system-role messages (2026-08-24 decision-log entry). Still deferred: `stdio` MCP transports for user-configured servers, the Codex and Gemini serializers for user-configured MCP servers, skills for non-Claude-runner providers, claude.ai skill sync, and token/cost metering (runners capture `usage` into result.json; `parseCodexResult` discards it).

The following capabilities require a separate trusted agent-runtime and repository integration and are intentionally not simulated:

- Agent-authored chat messages. (Provider and model selection are implemented: the dialog offers every provider whose rollout flag is on and every model in that provider's closed `PROVIDER_MODELS` allowlist. User-managed provider credentials are implemented — per-user encrypted keys in `user_provider_credentials`, resolved per run as agent-owner-key-else-server-key. See AGENTS.md's 2026-08-21 and 2026-08-24 decision-log entries.)
- Deployment and generic support for merge queues or non-squash merge methods.
- Generic artifact download UI beyond the per-run raw-log and session-brief expanders.
- Agent ownership transfer, and queue completion/removal. Task, model, and billing-credential edits are implemented (partial agent PATCH; billing changes refuse with `409` while a run is in flight), as are Pause/Stop/Delete for persistent agents and Pause/Stop for generated workers (any member; owner-only bulk pause-all/resume-all/stop-all) via nullable `paused_at` and the existing `deprovisioned_at`. Pause lets a current run finish; Stop also pauses, but cancels that run only for an owner caller. Provider stays uneditable by design — delete and recreate. Per-agent reasoning effort (`output_config.effort`) stays deferred: the runners do not thread a second axis today. Generated workers remain system-metadata-owned, non-editable, and non-deletable; Concierge activation/retirement and concurrent allocation remain exclusively router-controlled.

Repository connection, active candidate/PR identity, bounded latest-preflight data, conflict cases/questions, auto-dispatch/provision/provider settings, active agents, and the latest 20 caller-visible run summaries are included in `FloorSnapshot`; full logs and bundles remain excluded. Queue items carry a separate caller-specific rollback descriptor so older integrated prompts remain actionable beyond that run-summary bound. Candidate-wide Review contribution summaries/details are fetched through paginated member-authorized routes (25 by default, 100 maximum), not packed into `FloorSnapshot`. Deprovisioned generated agents are hidden from active targeting and context, while historical queue/run attribution remains visible. Run branches, publication/integration SHAs, conflict attempts, and independent attribution stay visible. Resolved source conflicts no longer remain as active Review warnings.

## Live run activity streaming

Runs stream a bounded activity feed while Codex executes. The in-sandbox runner (`scripts/codex-runner.mjs`) normalizes Codex thread events (reasoning, commands, file edits, agent messages, MCP tool calls, errors) and POSTs batches to `POST /runtime/run/events`, authenticated by a run-scoped gateway token with the `events` operation and gated on run status `running`/`cancel_requested`. Events persist in `agent_run_events` with runner sequences starting at 1,000,000; coarse workflow-stage events keep the per-run `MAX+1` scheme, so the merged timeline stays chronological under `ORDER BY sequence`. Accepted events broadcast to session members as a `run.activity` presence event without bumping `floor_revision`; members catch up or paint initial state via `GET /api/sessions/:id/runs/:runId/events?after=<sequence>`. Bounds: detail ≤ 2,000 chars, ≤ 50 events and 256 KB per POST, ≤ 2,000 runner events per run with a `truncated` sentinel; telemetry failures never fail the run.

## Session context and the live re-read tool

Every dispatched agent's prompt is a unified session brief (`db/session-context.ts` + `lib/session-context.ts`): its own request, every other agent and human on the floor, already-integrated work, other runs in flight with their live file edits, the rest of the queue, blocked/failed runs, and recent public team chat — bounded to 24,000 characters, direct messages structurally excluded (the D1 read never takes a `userId`). The exact rendered prompt is persisted as an `agent_run_artifacts` row of kind `prompt` and visible via a second Agent-card expander. A long run can re-read current floor state through a read-only `openfloor_session_context` MCP tool exposed by the Sandbox (`scripts/openfloor-mcp.mjs`), backed by `GET /runtime/run/context` (a `"context"`-operation gateway token, 60-minute TTL). Pooled run sandboxes are keyed by `RUN_SANDBOX_IMAGE_VERSION` so a stale pooled container can never be claimed by a live run after a `Dockerfile.sandbox` change — bump that constant whenever the image's contents change.

## Credential kinds — deliberately deferred pieces

Per-user credentials are keyed `(user_id, provider, kind)` with kinds `api_key` and `oauth` (pasted Claude setup token / ChatGPT auth bundle), and each agent's `credential_kind` names which one its runs bill. Anthropic setup tokens are fully live: validated on connect and sent upstream in their native form (Bearer + merged `oauth-2025-04-20` beta flag). Deliberately not built: ChatGPT-subscription Codex runs (the standing brief's §5, gated on Spike D, which has not run — the openai `oauth` kind is withheld from Settings entirely (`credentialKindsForProvider`) until §5 ships, and the openai gateway additionally refuses oauth-kind runs with a clear `503` as defense in depth for hand-written rows, so a bundle, refresh token included, never leaves as a header); more than one row per user+provider+kind (raising the ceiling later means a nickname column and a picker, not another recreate); automatic failover between a member's own two credentials on a rate-limit response (rejected: it switches billing ledgers mid-run); snapshotting `credential_kind` onto `agent_runs` (rejected: the in-flight `409` guard on billing edits makes it unnecessary, and it would be a migration plus a second source of truth for whose credential a run bills); fetching live model lists from vendor endpoints at dialog render, and modeling plan entitlements (the closed `PROVIDER_MODELS` constant is deliberately stale-able — a new model is a code change, not a broken run); showing a member their remaining subscription quota or another member's connection status (no authoritative source; not the creator's to see).

## Grok (xAI) — excluded three times, on every known route

The Anthropic-compat route died on xAI rejecting system-role messages (2026-08-24 decision log); the Responses route died the same day on xAI rejecting the `"content": null` Codex 0.148.0 writes on replayed reasoning input items (400 "Could not decode the compaction blob" on every thread's second request — Spike B). The 2026-08-26 re-spike (ENG-118) closed the rest: both failures reproduce byte-identically today; the chat wire is gone from the Codex binary itself (`@openai/codex-sdk@0.149.1`, the latest, vendors `` `wire_api = "chat"` is no longer supported. ``); reasoning effort `none` is vendor-rejected (`This model does not support 'reasoning_effort' value 'none'.` for grok-4.5 and grok-4.6); and the SuperGrok/X Premium subscription credential (Grok Build's `~/.grok/auth.json` OAuth bundle) is short-lived + refresh-based, so it fails the paste-a-credential requirements. All blockers are upstream (xAI tolerance or a Codex serialization change); gateway body rewriting stays rejected. `parseCredentialProvider("grok")` stays pinned null. Reopen conditions are enumerated in the 2026-08-26 decision-log entry.

## Deployment order

1. Run `npm test`.
2. Apply D1 migrations with `npx wrangler d1 migrations apply DB --remote`.
3. Build with `npm run build`.
4. Deploy with `npx wrangler deploy --config dist/server/wrangler.json`.
5. Smoke-test the owner/member flow from `docs/github-production.md` against only the disposable acceptance repository, including two consecutive integrations into one draft PR, automatic multi-file conflict resolution, a resolver question answered by an original author or owner, unrelated-member waiting UI, owner-only manual resolution with automation off, ready-for-review, protected squash merge, exact-SHA cleanup, a fresh candidate cycle, reload recovery, cancellation, and a failing retryable run.

Known follow-up: Phase 5 discard is still reported by the production UI as unsuccessful in the acceptance repository after the authentication correction. Keep its expected-SHA safety checks intact and diagnose it in the separately requested ticket; it is not part of Phase 6 acceptance.
